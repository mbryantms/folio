# label | table | why the seq scan is the right plan — read by explain_report.py.
# Entries are reviewed exceptions to the ≥ 5,000-row seq-scan gate; keep
# them few and specific. Removing one is always safe (the gate re-arms).
similar-large-cold | series_tags | stress-fixture series each carry all 8 tags, so the overlap's tag arm joins every series_tags row (20,000 of 20,000); real libraries' tags are sparse and take series_tags_pkey
duplicates-cold | issues | the memo miss groups the whole library: `count(*) OVER (PARTITION BY …)` over every live issue of the one library, which is the full table here; memoised per library (api::duplicates::DuplicateGroupsCache), so the warm and deeper pages never run it
library-stats-all | issues | the admin library list totals every library at once: one `GROUP BY library_id` pass that reads every issue row (counts by state plus `SUM(file_size)`, and `file_size` is in no index), so a full scan is the plan; it runs once per admin page load
library-stats-one | issues | the one-library form narrows on `issues_library_idx`, but the fixture holds a single library, so the filter matches every row and the planner rightly reads the heap sequentially; in a multi-library install it reads only that library's rows
similar-large-cold | series_characters | same fixture cause as the series_tags entry: every stress series shares the large series' tags, so the candidate set is all 2,500 series and the breadth-damping size query (`similarity::fetch_sizes`) counts characters for every series; the warm request reads the neighbour cache instead
